# ai-workspace init

> **Paths and tools.** `${CLAUDE_PLUGIN_ROOT}` is this plugin's folder and `${CLAUDE_SKILL_DIR}` the folder
> of this file. If they appear literally (not replaced, e.g. in Cursor), use `$AI_WORKSPACE_PLUGIN_ROOT`
> when it is set, otherwise the folder two levels above this file; for `${CLAUDE_SKILL_DIR}`, this file's
> folder. If there is no AskUserQuestion tool, ask in plain text with numbered options and wait for the answer.

Arguments: `$ARGUMENTS` — optional codebase names to limit a refresh to. Empty means all codebases.

Plugin files: `${CLAUDE_PLUGIN_ROOT}` (templates in `templates/`, scripts in `scripts/`).
Workspace root: the current project directory. All generated paths below are relative to it.
Path terms (`<clone>`, components, worktrees) are defined in `${CLAUDE_PLUGIN_ROOT}/skills/task/references/layout.md`.

Generated files carry the marker line `<!-- generated by ai-workspace:init -->`. **Only overwrite a file
that still has the marker.** If a file exists without it, the user owns it: leave it and list it in the summary.

## 1. Questions

Ask in **this order**; each answer feeds the next. With an existing `workspace.yaml`, keep every answer
in it and ask only what is missing or empty, then continue with the steps that were skipped.

**How to ask.** Questions are for people, not for config files:
- Plain words in questions, options and descriptions. Never show config values or jargon there (no
  `tools: [...]`, `type: gitlab`, `custom`, "MCP", "adapter"); they belong only in `workspace.yaml`.
- The option prompt holds at most 4 options and always adds its own free-text choice; don't add an
  "Other" of your own. **When the expected answer is free text, ask in plain text without an option
  list** (the options would hide the main answer).
- A follow-up that narrows an earlier answer **continues that question**: same header, and say what
  the user picked. If a free-text answer already settles it, map it and skip the follow-up.
- Never throw answers away: if something can't be answered now, save the rest and say how to finish.

### Q1. Mode (only if the current folder is a git repository)
*"This folder is a git repository. Set up the workspace for it alone?"* **This repository only** →
`mode: single` (codebase `path: "."`, nothing cloned; skip Q3) / **Several repositories** → `mode: multi`.
If the folder is not a git repository: `mode: multi`, no question.

### Q2. Name
Propose the folder name: *"Name this workspace `<folder>`?"* **Use `<folder>`** / free text.

### Q3. Repositories (multi mode) — plain text, no option list
*"Paste the link of each repository this workspace should include: one or several, in any format
(one per line, or separated by spaces or commas). Folders already on your disk work too."*

Parse the answer with the script, never by hand:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/parse_repos.py" [--existing <names already in workspace.yaml>] <<'REPOS'
<the user's answer, verbatim>
REPOS
```

It returns `[{name, url}]` with names taken from the links. Show the list as
`backend ← git@gitlab.example.com:payroll/backend.git` and ask (same header): **Looks right** / **Add
more** / **Change a name** / free text. For removals or edits, apply them and show the list again.

If nothing was found (exit code 2), or the user says they don't have the links yet, continue the same
question: *"No repository links yet. How do you want to continue?"* **Add them later** (save everything
else with `codebases: []`) / **Use a folder on my disk** (ask for the path) / **Try the demo
repositories** (your answers so far are saved; run `bash "${CLAUDE_PLUGIN_ROOT}/examples/demo/setup.sh"
<folder>` there, and point the user to it).

Base branches are not asked: they are read from each clone in step 2.

### Q4. Code hosting
Take the hostname from the links (`git@gitlab.example.com:group/app.git` → `gitlab.example.com`) and
ask *"Where is your code hosted?"*, pre-selecting what the links suggest:
1. **GitHub** (github.com or GitHub Enterprise) → `type: github`; `url: https://<host>` for Enterprise.
2. **Another git server** (GitLab, self-hosted GitLab, Bitbucket, Gitea, Azure DevOps, …) → if the
   hostname contains `gitlab`, or the user confirms (continuation: *"Is `<host>` a GitLab server?"*),
   `type: gitlab`, because GitLab opens MRs from `git push`; otherwise `type: other` (pushes, then a link
   to open the PR). Set `url: https://<host>` unless it is gitlab.com; ask for the web address only if it
   can't be derived.
3. **Nowhere, local only** → `type: none`: nothing is ever pushed.
Repositories on several hosts: one host setting applies to all; ask which one. No links (repositories
later): ask the same question without a pre-selection.

### Q5. Tasks
1. *"Where do you keep your tasks?"* **Jira** / **GitHub Issues** / **Trello** / **Somewhere else**
   ("Task files, your company's own tool, or no tracker at all").
2. After *Somewhere else*, continuing (same header): *"Not Jira, GitHub or Trello: where do you keep
   them?"* **Task files in this workspace** ("Simple files like backlog/task1.md; their status is updated
   in the file") → `markdown` / **Our own tool** ("Your company's tracker, connected through a small
   script") → `custom` / **No tracker** ("Describe each task when you start it") → `none`.

Then ask only what can't be derived, in plain words:

| Tracker | Ask | Don't ask (defaults) |
|---|---|---|
| Jira | site address (`https://your-company.atlassian.net`), project key, the status names for "work started" and "in review" | how to connect: use a connected Atlassian MCP server if there is one, else the API token (explain the two `export` lines in the summary); the acceptance-criteria field (optional setting, mention it) |
| GitHub Issues | which repository holds the issues, only if the links contain more than one GitHub repository | the repository when there's one; labels `in-progress` / `in-review` |
| Trello | the list names for "work started" and "in review" | credentials (explain the two `export` lines in the summary) |
| Task files | nothing | folder `backlog`, statuses `in-progress` / `in-review`; create `backlog/` with one example task |
| Our own tool | continuation: *"Is a connector for it already available?"* **Yes, a script** (ask for its three commands) / **Yes, an MCP server** (ask its name) / **Not yet** | with *Not yet*: save `type: custom` without commands (= not connected yet). Tasks are described by hand until it exists. Offer: "Share its API documentation and I'll write the connector" (see `${CLAUDE_PLUGIN_ROOT}/skills/task/references/trackers.md`, custom) |
| No tracker | nothing | |

Offer only these trackers; don't suggest others (for example GitLab issues) that have no adapter.

### Q6. Pipelines (skip for local only → `ci.provider: none`)
*"What runs your pipelines?"* Offer only choices that work with the host from Q4:
- GitHub or GitLab: **GitHub Actions** / **GitLab CI** (whichever matches, → `host`) / **Jenkins** /
  **Something else** / **None**. That's four options: the host's own CI, Jenkins, something else, none.
- Another git server that isn't GitLab: **Jenkins** / **Something else** / **None** (its own pipelines
  can't be read).

**Jenkins** → ask only its address now (`ci.url`); job names come in step 3b, after cloning, when the
repositories and any monorepo parts are known. **Something else** (TeamCity, Bamboo, Azure Pipelines, …)
→ `custom`, continuing: *"Is a script for it available?"* **Yes** (ask for its status / log / rerun
commands) / **Not yet** (save `provider: custom` without commands = not connected; `/ai-workspace:ci`
explains this until it exists). **None** → `none`.

### Q7. Confirm and save
Summarise in plain words, not YAML, e.g. *"Workspace payroll: 3 repositories on
gitlab.oodleslab.com (backend, frontend, mobile), tasks in Jira project PAY, pipelines on Jenkins, MRs
opened through git push."* Then **Save** / **Change something** / **Show the file**. Write
`workspace.yaml` from `templates/workspace.yaml` on *Save*.

Not asked (defaults, mention in the summary where useful): which AI tools (set from the tool running
this skill: `[claude-code]` in Claude Code, `[cursor]` in Cursor; add the other when its files already
exist or `workspace.yaml` lists it), worktrees (`false`), protected branches, gates, guard.

### Checks (warnings only; never block saving)
- Validate: `version: 1`; `mode` multi or single (single: one codebase with `path: "."`); names unique
  and matching `^[A-Za-z0-9._-]+$`; multi mode: every codebase has a `url`; component `dir`s exist after
  cloning and stay inside the repository; every name in `ci.shared_jobs[].codebases` is a codebase; the
  tracker has its required fields (jira: `base_url`; github: `repo`; markdown: `path`; custom: may be
  unconnected). If something is invalid, save what is valid and ask about the rest.
- Tracker reachable, without printing secrets: jira over the API and trello need `JIRA_API_TOKEN`
  (+ `JIRA_EMAIL` on Cloud) / `TRELLO_API_KEY` + `TRELLO_TOKEN`; github needs `gh auth status`;
  markdown needs its folder; an MCP server must be connected.
- Jenkins: `JENKINS_USER` and `JENKINS_TOKEN` exist (never print them).
- Git host CLI (skip for local only): `gh` for GitHub, `glab` for GitLab, logged in to the right host
  (`gh auth status --hostname <host>` / `glab auth status --hostname <host>`). Without `glab`: MRs still
  open through git push options; `glab` adds descriptions, CI and review follow-up
  (`brew install glab`, then `glab auth login --hostname <host>`).

**No repositories yet:** skip steps 2–5, do step 6 (workspace files, settings, folders), and in the
summary say exactly how to continue: run `/ai-workspace:init` again and paste the links (nothing else is
asked again), or add them under `codebases:` in `workspace.yaml`.

## 2. Clone

Single mode: nothing to clone. Multi mode: for each selected codebase run, one at a time:

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/clone-repo.sh" "<root>" "<name>" "<url>" "<branch-or-empty>"
```

The script is idempotent (fetches if already cloned). On failure (auth, wrong URL) record the error,
continue with the rest, and report at the end. Never embed credentials in URLs.

## 3. Detect (parallel)

Dispatch **one Explore subagent per unit, all in a single message**: one per codebase, or one per
component for codebases with `components`. If a single-codebase repository looks like a monorepo
(several apps/services with their own build files, e.g. `apps/*`, `services/*`, `packages/*`, a
workspace config such as `pnpm-workspace.yaml`, `nx.json`, `turbo.json`, `go.work`, Maven modules),
first propose components to the user. Give each subagent this brief with `<path>` filled in
(`<clone>` or `<clone>/<dir>`):

> Analyse `<path>` (read-only). Determine from evidence, not guesses: primary and secondary
> languages; frameworks; build tool and wrapper; test framework; package manager (from lockfiles);
> lint/format tools; exact commands for install, build, test-all, test-single, lint, run — taken from
> build files, package scripts, Makefile/Taskfile, CI config (`.gitlab-ci.yml`, `.github/workflows`,
> `Jenkinsfile`), Dockerfile and README; entry points; where tests live; integrations with other services
> (HTTP clients, API base URLs, queues, DBs) with file paths; conventions visible in code (layering,
> naming, DI, state management, error handling). Mark anything not confirmed from files as `(unverified)`.
> Return a concise structured report; under 400 words.

## 3b. Questions that need the repositories

Ask these only now, when the repositories are cloned and analysed. Save each answer to `workspace.yaml`.

1. **Monorepo parts.** If a repository looks like a monorepo (see step 3), continue: *"`platform` contains
   several apps: services/api, apps/web, packages/shared. Treat them as separate parts?"* **Yes** /
   **Yes, but change the list** / **No**. With yes, record `components` and analyse each part.
2. **Base branches.** The clone step reports each repository's default branch. If they are all the same,
   set `git_host.default_branch` to it; set `branch:` on repositories that differ. Mention the result in
   the summary; ask only if a repository has no default branch.
3. **Jenkins job names** (`ci.provider: jenkins`):
   - Ask for the Jenkins job of **one** repository (plain text, e.g. `payroll/backend`), compare it with
     that repository's link, and propose `ci.job_pattern` (placeholders: `{group}` full namespace,
     `{owner}` its first part, `{repo}`, `{codebase}`). For monorepo parts with their own jobs, propose
     `ci.component_job_pattern` the same way (e.g. `{repo}/{component}`).
   - Resolve every repository and part with `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ci.py" job …`
     (see the ci skill) and show the list: "backend → payroll/backend, frontend → payroll/frontend". Ask
     **All correct** / **Some are different** (then ask which, and record `ci_job:` only for those).
     If names follow no pattern, record one `ci_job` per repository.
   - *"Does any Jenkins job build several of these repositories together (integration, end-to-end)?"*
     **No** / **Yes** (ask its job path and which repositories; ask for branch parameters only if it is
     started with them, e.g. `BACKEND_BRANCH: "{branch:backend}"`). Repositories built only by such a
     job get `ci_job: none`.

## 4. Profiles

For each unit write a profile from `templates/profile.md`, filling it from the subagent report:
`context/codebases/<name>.md` for a codebase, `context/codebases/<codebase>--<component>.md` for a component.
`{{PATH}}` is the unit's path from the workspace root (`codebase/api`, `.`, `codebase/platform/apps/web`);
commands are written as `cd {{PATH}} && ...`. `generated_from` = `git -C <clone> rev-parse --short HEAD`;
`generated_at` = today.
Put the marker line right after the frontmatter. Keep each profile under ~80 lines.

## 5. Path-scoped rules

Rules load only when Claude works on matching files. For each unit (file prefix `<unit>` = codebase
name, or `<codebase>--<component>`), in `.claude/rules/`:

- `codebase-<unit>.md` from `templates/rules/_codebase.md`.
- For each detected language/framework that has a template in `templates/rules/`
  (java, kotlin, typescript, javascript, angular, react, python, go, php, dart-flutter, csharp):
  `<unit>-<template>.md`, scoped to the unit and the relevant extensions.

**Globs must cover every place the unit's files can be edited**, the main clone and task worktrees:

| Mode | Globs for unit files (example: TypeScript) |
|---|---|
| multi | `"codebase/<name>[/<dir>]/**/*.{ts,tsx}"` and `"work/*/<name>[/<dir>]/**/*.{ts,tsx}"` |
| single | `"[<dir>/]**/*.{ts,tsx}"`; this also matches task worktrees under `.ai-work/`, which is intended |

Replace `{{PATHS}}` with a YAML list (one `  - "glob"` per line), `{{NAME}}` with the unit name,
`{{PATH}}` with its path, and `{{PROFILE}}` with the profile file name without `.md`.
Insert the marker line right after the frontmatter. For a stack with no template, skip it and mention it
in the summary as a candidate template to contribute.

Write the rules for each tool in `tools`:
- **claude-code**: `.claude/rules/<file>.md` as above (`paths:` frontmatter).
- **cursor**: the same rule as `.cursor/rules/<file>.mdc`, with Cursor's frontmatter instead of `paths:`:

  ```markdown
  ---
  description: <the rule's first heading, e.g. "Python rules for codebase api">
  globs: ["codebase/api/**/*.py", "work/*/api/**/*.py"]
  alwaysApply: false
  ---
  ```

  Same globs, same body, same marker line.

## 6. Workspace files

- Workspace instructions from `templates/CLAUDE.md`. Placeholders: `{{WORKSPACE_NAME}}`, `{{TRACKER}}`
  (type, or "none configured"), `{{GIT_HOST}}`, `{{PROTECTED}}` (comma-separated), `{{CODEBASE_TABLE}}`
  (units: name · path · stack · one-line purpose · profile link), and `{{WORKTREE_NOTE}}`: when
  `worktrees: true`, `; with worktrees enabled, a task's changes live in work/<KEY>/<name>` (single mode:
  `.ai-work/<KEY>`), else empty. Add the marker. Keep it short.
  - multi mode, `tools` without cursor: write it as `CLAUDE.md` in the workspace root.
  - multi mode, `tools` with cursor: write it as `AGENTS.md` (Cursor reads it automatically). If
    claude-code is also in `tools`, write `CLAUDE.md` as just the marker line plus `@AGENTS.md`, so both
    tools read one file.
  - single mode: the repository may already have its own `CLAUDE.md` or `AGENTS.md`, so never touch
    them. Write `.claude/rules/ai-workspace.md` (no `paths:` frontmatter, so it always loads) for
    claude-code, and `.cursor/rules/ai-workspace.mdc` with `alwaysApply: true` for cursor.
- Ignore files:
  - multi mode: ensure every line of `templates/gitignore` is in `.gitignore`; don't remove existing lines.
  - single mode: don't edit the team's `.gitignore`. Exclude the workspace files locally with
    `bash "${CLAUDE_PLUGIN_ROOT}/scripts/exclude-local.sh" . /workspace.yaml /context/ /tasks/ /.ai-work/ <each generated .claude/rules and .cursor/rules file>`
    (writes `.git/info/exclude`, idempotent). Mention that the team can commit them later if they want
    to share the setup.
- Settings (claude-code only; Cursor keeps its permissions in its own settings, and the guard hook
  protects both): in multi mode `.claude/settings.json`; in **single mode `.claude/settings.local.json`**
  (the repository may commit `.claude/settings.json`, and single mode must not change tracked files).
  Merge (never replace) — add `"ai-workspace@ai-workspace": true` under
  `enabledPlugins` and the `permissions.allow` / `permissions.deny` entries from `templates/settings.json`
  (read-only git commands are pre-approved; force-push, hard reset, clean, merges and reading `.env`
  files are denied). Add the
  `extraKnownMarketplaces` block only if `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json` has a
  `repository` field; replace `{{PLUGIN_REPO}}` with its `owner/repo`.
- Create `tasks/` and `context/` (and `work/` in multi mode with worktrees) if missing.
- Task files tracker: if the folder (default `backlog/`) doesn't exist, create it with `example.md`:
  frontmatter `id: T-1`, `status: todo`, `type: feature`; a `# Title`, one line of description, and
  `## Acceptance criteria` with two `- [ ]` items, so the user sees the format.
- Multi mode: if the workspace root is not a git repository, run `git init` there (do not commit).

## 7. Summary

Report a table: codebase · cloned/updated/failed · base branch · stack · test command · rules written. If only one
AI tool is set up, add one line: "Colleagues using Cursor (or Claude Code)? They can run
`/ai-workspace:init` once from their tool, or add it to `tools:` in `workspace.yaml`." Then list
skipped user-owned files, clone failures with the error, unverified commands, and stacks without a
rule template. Suggest next steps: `/ai-workspace:doctor`, then `/ai-workspace:status`, then work a ticket.
